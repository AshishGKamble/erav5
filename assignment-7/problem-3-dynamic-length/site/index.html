Dynamic length / ERA V5 · Assignment 7 · Problem 3
Kronecker embeddings · the fixed 32 byte window

The window is two problems, and only one of them is about waste.

The assignment says a 32 position window wastes space and crops long words. Both are true, and they are not equally serious. The waste is enormous and harmless. The cropping is smaller and it is not script neutral: the window is counted in bytes while language is written in characters, and every Indic script costs exactly three bytes per character against Latin's one. Every number on this page is computed by a script in src/ and read from artifacts/.

TL;DR

The answer to each of the three questions

The brief asks three things. All three are answered below, and the rest of this page is how those answers were arrived at, in the order the experiments ran.

Q

What the assignment asked

The briefToday Kronecker is limiting to presenting 32 position for every work (even "apple" or "a" as well). That's a waste of space. What can we do? How can it be dynamic and doesn't force us to crop a word (currently we cannot have a word of len more than 32).

Three questions: the waste, the dynamism, and the cropping. This page answers all three, and argues the third is the one that matters.

E1

The waste is real, and it is the least interesting fact here

Occupancy is the share of the window a token actually fills. Everything else is zeros.

E2

The window is counted in the wrong unit

Bytes per character is exactly 3.000 for all nine Indic scripts, not approximately. Measured in graphemes, which is what a reader perceives, the gap is wider still, because Indic conjuncts are written with several codepoints and read as one.

characters in a 32 byte window graphemes in the same window
E3

The harm: two words, one embedding

A truncation collision is two distinct words identical in their first L bytes. They produce byte for byte identical codec vectors, so no model at any depth can tell them apart. Verified, not argued: 200 of 200 sampled pairs differ by exactly 0.0.

These are grammar, not curiosities

Indic languages mark case, number and person with suffixes. The window reads prefixes. It is discarding the half of the word that carries the grammar.

⚠

Two corrections that cut against this finding

A first pass measured a much higher English collision rate, which would have made the gap look smaller and the measurement look careless. Two things were wrong with it, and fixing both widened the gap.

E4

Three fixes, compared at identical cost

A byte window of L costs 256L dimensions and a two block codepoint window of L costs 512L, so byte L=32 and codepoint L=16 are both D=8192 and compare with nothing left over. Fix B helps every Indic script and makes Latin worse. Fix D, which the measurement found rather than the plan, helps Indic and leaves Latin exactly where it was.

byte L=32, published fix B, codepoint L=16 fix D, script relative L=32
E7

The cheapest fix, which the data pointed at

Every collision is a shared prefix with a differing suffix. So spend half the window on the front of the word and half on the back. Same dimensions, same structure, no new parameters, no script table, no Unicode assumptions. Only a different choice of which bytes to encode.

If only one change is made, it should be this one. Fix D is better in absolute terms but needs a script table, a per token tag, and an assumption about Unicode block layout that this corpus happens to satisfy. Reading both ends needs none of that, and the two compose.
E6

"Waste of space" means three things

Saying the waste is benign is true about accuracy and evades the question, which is about space. Space means three different things here, with three different answers.

Is it already dynamic? Cost against token length

If the window charged every token for all L positions this line would be flat. It is not flat. "a" costs one row lookup and a thirty byte word costs thirty.

E5

The downstream test, and why it could not work

The pre-registered experiment trained the same model with each codec. The result was null on both lanes. A null is worth nothing without knowing why, so the exposure was measured.

E5b

The same test rebuilt so it can see the effect

Words as units instead of BPE tokens, and a tied byte head so there are zero per word output parameters. The metric is exact full word reconstruction, with truncated targets counted as failures rather than dropped from the denominator.

⚙

How this was measured

Several of these exist because a naive version of the same measurement gave a wrong answer first. Those are marked, because the reason a technique is needed is usually more informative than the technique.

techniquewhat it is for
Script detection from unicodedata.name Derive a character's script from the Unicode database rather than a hand written table, so the classification cannot be accused of being tuned to produce this result.
Extended grapheme approximation Count what a reader perceives as one unit: a base character plus its combining marks, plus consonants joined by a virama. No segmentation dependency was added.
Prefix grouping Group distinct word types by their first L bytes. Any group larger than one is a set of words that receive the identical embedding.
Bitwise verification Re-encode colliding pairs and compare the actual float vectors, instead of trusting that the definition implies it.
Equal-D comparison Charge every codec the same dimension budget, so no fix can look good merely by spending more. A byte window of L costs 256L and a two block codepoint window costs 512L.
Shannon entropy per base-256 digit Measure how much information a codec block actually carries. This is the measurement that exposed fix D.
Affine factorisation of z-normalisation A code is a sparse support plus two closed form scalars, exact to 1.4e-14. This is why memory and compute are not actually paid.
Gather plus segmented reduction Needed because a per token Python loop loses a wall clock race to dense BLAS despite doing far less arithmetic, and reporting that would measure the implementation rather than the construction.
Seed noise floor Repeat every trained comparison across seeds and report any effect inside two standard deviations as not established.
Exposure diagnostic Needed because E5's null turned out to be a measurement with no exposure to the effect, rather than a finding about the codecs.
Lane separation and punctuation stripping Needed because pooled Latin first measured a far higher collision rate, almost all of it source code and trailing commas.

What is not claimed. Everything trained here is 2 layers at d_model=96 on CPU, with every effect quoted against a measured seed noise floor. Fix D's assumption that a script uses one Unicode block is measured in this corpus and is not a property of Unicode. Grapheme counts are approximated and are used only to size the codepoint to grapheme gap. Timing figures are re-measured on each run and move with machine load; every collision count is exact.
