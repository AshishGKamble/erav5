An India-first 40B model, designed around one number.

A 40B model runs out of compute at ~800B tokens - but out of real Indian words long before that. Gemma 4 (Apr 2026) is now frontier-strong and even agentic, so we match it on capability with a license-clean 2026 recipe, and win on what a global 140-language model does not do: an India-first perspective, measured Indic depth, and Indic tokenizer efficiency. The lever underneath is still fertility - tokens per word.

01

What "winning" means

The briefas good as (or better than) Gemma 4, and really good at coding, agentic work and Indic languages.

Gemma 4 (Apr 2026) is a big jump over Gemma 3 - frontier scores and now native agentic. We target parity with the 31B flagship on its own suite, and lead where it stays silent: the Indic depth it no longer reports. (Our 40B dense vs Gemma 4's 31B dense flagship.)

The goalposts moved - so our wedges are positional, not capability gaps. Gemma 4 is frontier and agentic, so we concede capability parity and win on three durable fronts: (1) India-first perspective - Gemma has none; (2) measured Indic depth - Gemma 4 publishes only a blended MMMLU 88.4, zero per-language; (3) tokenizer efficiency - focus beats breadth (Section 4).
02

The data: what we feed it, and why

The briefhow would your data look, what would you collect and why - for pre-training, post-training and RL / alignment?

Matching Gemma 4 needs frontier reasoning, which wants 40%+ code + math - fighting the India tilt. So we stage the data instead of one flat mix, and add a reasoning + agentic training spine the naive plan lacked.

The brief asks for three data stages. Here is each, and why:

Pre-training

Reasoning base, then Indic depth

Code / math-rich base (The Stack v2 rewritten, OpenWebMath) + Indian-weighted English (NCERT, PIB, law), then a dedicated Indic continued-pretrain stage.

Post-training (SFT)

Reason, then help in Indian tools

Reasoning cold-start distilled from R1 / Qwen3 (license-clean), plus native + translated Indic instructions and agentic data re-skinned to IRCTC / UPI / DigiLocker.

RL / alignment

Where preference comes from

RLVR (math exact-match, code unit-tests) + multi-turn agentic RL, then an Indian-Constitution value set (Constitutional AI) + a seed of native-annotator preferences.

Two named limitations. The Indic slice is ~90% synthetic, so Indic quality is capped by our translation / synthesis quality. And the τ²-bench ~77 target is aggressive - at or above the current open frontier (Kimi K2 ~66); it hinges on heavy agentic RL or a strong agentic teacher.
03

Cleaning: tuned for Indian text

The briefhow would you clean your data for the objectives you defined?

The web is ~90% junk, so we run the usual scrub. The value is in four traps that ordinary English pipelines get wrong and that quietly destroy Indian data - plus hard decontamination against Gemma 4's newer benchmarks.

  • Trap 1 - deleted Hinglish. A naive "is this English?" gate throws away Hindi written in Latin letters. We use India-aware language detection.
  • Trap 2 - corrupted scripts. The common NFKC normalization silently rewrites Indian characters. We use NFC (learned the hard way in Assignment 2).
  • Trap 3 - unfair quality bars. One English-tuned threshold over-deletes small languages, so we set the bar per language.
  • Trap 4 - harmful global de-duplication. De-duping across everything strips good older data, so we do it within each source.
04

The tokenizer: fertility targets & vocab size

The briefwhat fertility for each language, and for coding, science, math and agentic tasks - and from those numbers, the tokenizer size?

Fertility = pieces per word (lower is better). Ordinary tokenizers shatter Indian scripts - Llama-4 needs 10.5 tokens for one Odia word. Tellingly, Gemma 4 reuses the exact same 262K tokenizer as Gemma 3, spread across 140+ languages. Our fix: a focused vocabulary - focus beats breadth.

200K, reached three ways that agree. A bottom-up count (~50K shared + ~144K across 12 languages) ≈ 196K · the vocabulary-scaling law for a 40B (~160K + a multilingual premium) · and real-world proof: IndicSuperTokenizer already hits Hindi 1.23 / Tamil 2.12 at exactly 200K - versus Gemma 4's 262K.

Which languages, and their fertility targets

The tutor anchored on the top 10 Indian languages by population and left the selection to us. We commit to 12: the top 10 (which already includes Urdu at ~#7) plus Punjabi and Assamese - spanning both the Indo-Aryan and Dravidian families across ~10 scripts. Targets are set per language shape: Dravidian languages glue many word-parts into one long word, so a higher target is honest, not a failure.

Fertility for the other domains the brief asks about

Code

~1.45 pieces/word

Indentation carries meaning, so we add single-piece whitespace runs and a digit splitter (StarCoder-style).

Science

~1.2 - 1.3

Technical prose tokenizes near English; it reuses the math, Greek and SI-unit tokens, so it needs no separate budget.

Math

Deliberately higher

Numbers are split into single digits. It looks wasteful, but it is what makes arithmetic reliable - fertility traded for correctness.

Agentic

Structural, not linguistic

"Fertility for agents" is really JSON / tool-call overhead. Reserved special tokens keep each action cheap.

Faithfulness

Byte-fallback

Any unknown character falls back to raw bytes, so text is never lost - a lesson carried from Assignment 2.

05

Testing, and a benchmark we invent

The briefhow would you test your model against the objective, including an Indian perspective?

Three buckets, on Gemma 4's own harder suite. General-skill and Indian-language exams exist. The third - does it think from an Indian point of view? - has no good test, so we build one.

Bucket 1

General skills (Gemma 4's suite)

MMLU-Pro, AIME 2026, LiveCodeBench v6, GPQA Diamond, BBEH, MMMLU, and τ²-bench for agentic. Targets in Figure 1.

Bucket 2

Indian languages (our wedge)

MILU, IndicGenBench, IndicXTREME, Global-MMLU - reported per language, which Gemma 4 does not.

Bucket 3

Indian perspective

No good benchmark exists. We propose BharatDrishti - the original contribution below.

Two testing principles. Gemma 4 itself dropped the saturated classics (MATH, GSM8K, HumanEval) for harder successors - we follow suit and decontaminate against all of them. And report fertility itself as a result - the proof that the Section 04 tokenizer bet paid off.
