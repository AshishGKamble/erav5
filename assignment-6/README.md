## 1. What this assignment actually rewards

It reads like a data assignment. It is a **systems-determinism assignment**. Nothing is graded on
whether the model learns; the points are for proving invariants, and grading step 3 inspects the code
to confirm behaviour "was not simulated or hardcoded".

So one rule governs the design:

> **Every claim in `evidence.json` is recomputed from an artefact the run produced, never from a
> variable the run was holding at the time.**

Throughput is derived from the ledger, not a live counter. Mixture compliance comes from consumption
records, not from the scheduler's intentions. If it cannot be reconstructed afterwards, it is not
claimed.

## 2. The architectural spine

**A batch is a function of the frozen inputs and the consumption history.**

```
batch(step) = f(seed, plan_hash, manifest_hash, ledger[0:step])
```

Candidate draws come from a counter-based hash of `(seed, step, slot, attempt)`. There is no stateful
sampler whose RNG position must be saved and restored, so resume means *rebuild the scheduler state
from the ledger prefix and carry on*. Skipping or repeating a batch is not something this system
tests for - it is structurally unavailable.

**The honest caveat.** A deficit depends on everything consumed before it, so `batch(step)` is
**O(step) to reconstruct, not O(1) seekable**. The checkpoint therefore stores the scheduler state
*and its hash*, and resume recomputes that state from the ledger and asserts a match - O(1) trust,
O(n) verification, nothing believed on the strength of having been written down.

**What is hashed:** token ids, loss masks, position ids, segment ids, provenance spans, shard bytes,
tokenizer, plan, manifest. **What is never hashed:** loss, timings, throughput. Floating point shifts
with BLAS backend and thread count; hashing it would make a correct system fail its own replay check
on someone else's machine.

## 3. Proving the resume, without marking our own homework

The brief asks resume to "prove the next batch is exactly the expected batch". A checkpoint that
predicts its own next batch and then matches it is self-fulfilling.

So the demo trains the same 60 steps **twice** - once clean, once crashed at step 35 and resumed from
the checkpoint at step 20 - and asserts the two consumption ledgers agree record-for-record on batch
id, lane composition, token spans and hash. The oracle is external to the mechanism under test.

**And the losses agree too.** Adam's first- and second-moment estimates are checkpointed alongside
the weights, so the resumed run reproduces all **60 losses bit-identically** - worst difference
exactly `0.0`, including all 39 steps after the resume point. This matters more than it might look:
data equivalence alone would pass even with a fresh optimiser, because the batch stream does not
depend on model state. Loss equivalence is what proves the *training* resumed, not just the reader.

Three further checks make it hard to pass by accident:

- the resumed ledger is checked for **contiguity** (no skipped or repeated step);
- the partial tail written before the crash is **rewound** to the checkpoint's recorded offset, and
  the count of dropped records is logged;
- a **negative control**: resuming the same checkpoint against a tampered `plan.json` must be
  *refused*, because the checkpoint records the plan hash.

```
[PASS] scheduler_state_reconstructed   recomputed from 21 ledger records
[PASS] resume_next_batch_matched       step 21 hash a3787f93ab162dcf
[PASS] resume_rejects_modified_plan    refuses to resume against a different plan.json
[PASS] ledger_equivalence              60 batches compared record-for-record
[PASS] resume_reproduces_losses        60/60 losses bit-identical, worst delta 0.00e+00
```

## 4. Design decisions

### 4.1 Immutable shards

Same code, different machine, different day → byte-identical shards. Three rules buy it: documents
are **sorted by content-addressed id** before assignment (so a shard is a function of its document
*set*, not of corpus order); **nothing observed at run time** enters a shard; and splits are derived
from document content rather than position.

Shard files carry no hashes. Every hash lives in the manifest, so validation is a real cross-check -
recompute from bytes on disk and compare against an independent description. All three tamper paths
are caught by different mechanisms, which the test suite exercises:

| Attack | Caught by |
|---|---|
| flip one byte of token data | `content_sha256` |
| relabel an eval shard as train | `index_sha256` **and** shard identity |
| edit the manifest | manifest self-hash |

### 4.2 The evaluation firewall, enforced three times

A5 §9.2 lost a published finding to a validation leak - `prepare_data.py` repeated its source six
times before splitting validation off *by token offset*, so every held-out window also sat in
training and the reasoning metric was measuring memorisation. That failure was invisible because
nothing was checking. Here:

1. **Structural** - splits assigned from document content, so a document cannot land in two splits.
2. **Identity** - the split is hashed into the shard, so relabelling changes the hash.
3. **Admission** - checked at point of use, every refusal logged.

And the firewall **guards a live pool**. The candidate catalogue deliberately holds every split, so
**704 non-train documents** sit among the candidates and are refused at every draw during training -
not merely absent from consideration. An earlier version loaded train-only, which meant the check was
correct but could never fire, and "it never blocks anything" is not a demonstration. On top of that
the demo **attacks the firewall** with 15 real eval and holdout shards. An assertion that never fires
proves nothing.

### 4.3 Packing: four policies, seven lanes

Policy is the *splitting* rule; ordering is a separate axis (code is repo-ordered so related files
share a window; Indic is band-ordered so a sequence has one difficulty).

| Policy | Lanes | Rule |
|---|---|---|
| CONCAT | web | split freely; boundary loss is cheap, utilisation is worth more |
| DOC_ALIGNED | code, math, indic | whole documents where they fit; oversize read in contiguous windows |
| ATOMIC | reasoning, agentic | never truncate a **loss-bearing** span; split only between turns |
| LONG_DOC | long_ctx | one document per sequence, windowed, positions continue |

The ATOMIC rule is precise, and getting it precise mattered. "Never split a document" cost 39% of
the agentic lane at a 512-token window, because Glaive's system prompts alone exceed it. The correct
rule is **never split a loss-bearing span**: a masked context span - a wall of function schemas, a
tool dump - can be divided without teaching the model anything wrong, since it is not a target. Only
a chain of thought or a tool call must stay whole. That single distinction took the drop rate from
39% to 14%, and a test verifies all 777 loss-bearing spans survive intact.

Every sequence carries `loss_mask`, `segment_ids` (block-diagonal attention) and `position_ids` that
restart per document. Forgetting position restart or segment isolation is the classic packing bug:
the mask looks right, the numbers look plausible, and the model trains on cross-document nonsense.
The model-level test perturbs a token in one document and asserts another document's logits move by
**exactly zero**.

### 4.4 The lecture's two open questions, answered

**Separate Indic shards, or one shard mixed 10/90 with an OPUS override?** *Separate, flagged
protected.* A mixed shard rejected by OPUS loses the other 90% with it; OPUS judges from the first
~512 tokens, so a mixed shard's score is decided by whichever document happens to land first; and an
override must be attributable to a lane to be auditable.

**Indic curriculum - simple news first, or RBI and legal material?** *Register decides it.* Short
conversational exchanges are the easy end (B1); long procedural text - the register legal and
regulatory writing most resembles - is the hard end (B4). Thresholds come from the measured length
distribution, giving B1 29% / B2 41% / B3 27% / B4 3%.

### 4.5 Difficulty bands actually gate the curriculum

`plan.json` gives each stage a band range - Seed `B0-B1`, General `B1-B3`, Reasoning `B3-B4`,
Long-context `B4-B5`, Anneal `B5` - and every document carries a band. **2,597 candidate draws were
refused for sitting outside their stage's range.** Where gating would have starved a slot it is
relaxed rather than emitting nothing, and the 19 relaxations are counted.

An earlier version of this README claimed the curriculum gated on bands when the field was computed,
stored, and read by nothing. It is implemented now; the claim was retracted before it was true.

Bands come from token-length quantiles within a lane, except Indic which keeps its register-derived
band. **Length is a proxy for difficulty and is labelled as one** - a longer file holds more in
context, a longer derivation has more steps - but it is not a measure of conceptual difficulty, and
a serious system would score that directly.

### 4.6 The anneal reserve

A5 holds ~3% of the budget back for a final low-learning-rate pass, and the word that matters is
*reserve*: you cannot conjure Tier-A data in the last 3% if you already spent it. Here a document is
reserved if it is the hardest band, or native-tier Indic at B3 or above. **290 draws of reserved
documents were refused before the anneal stage** - the reserve is demonstrably held back, not
declared and then spent.

### 4.7 Deferral is a decision, not a label

The brief names four OPUS outcomes and deferral is the one easiest to fake. Candidates are pooled by
decision and slots are filled in preference order - **accepted first, then deferred, then the best
rejected**. Over the run: 405 slots filled from accepted candidates, **129 from deferred ones**, 17
by exhaustion fallback. A deferred document is "not now", and when the snapshot generation turns over
it is re-scored and may accept.

A cross-step deferral queue was considered and rejected, for a reason worth stating: it would make
the batch stream depend on state that cannot be rebuilt from the consumption ledger, which would
break replay from a mid-run offset. Everything here is derivable from `(seed, step, slot, attempt)`
and the frozen inputs.

## 5. What the measurements showed

### 5.1 OPUS would have deleted the entire Indic lane

Scoring 120 candidates per lane against a snapshot built from web, code and math - A5's "English- and
code-heavy proxy":

| Lane | Mean score | Without the override |
|---|---:|---|
| web | 0.7530 | - |
| agentic | 0.6635 | **18% lost** |
| code | 0.6556 | - |
| math | 0.5592 | - |
| reasoning | 0.4202 | - |
| **indic** | **0.0994** | **100% lost** |

A5 §5.1 argued the protected floor was necessary. This measures it: an English-and-code proxy reading
only the first 512 tokens does not under-rate Indic, it annihilates it.

**A finding for A5.** `plan.json` protects Indic and agentic. The exhaustion counts say the proxy
also systematically under-rates **reasoning**, **long-context** and **math**, which are not protected.
The protection list is incomplete.

### 5.2 Two trainable fractions diverge from the plan

| Lane | `plan.json` | Measured | Why |
|---|---:|---:|---|
| agentic | 0.35 | **0.507** | Glaive is function-calling chat, not the SWE-bench and terminal traces A5 sized |
| reasoning | 1.00 | **0.575** | the GSM8K prompt is masked; only the answer is a target |

Neither refutes A5. The first says the only permissively-licensed agentic corpus is the wrong shape -
which is what A5 §11 predicted when it ranked agentic as acquisition priority #1. The second says a
plan written about reasoning *traces* met a corpus of question-answer pairs.

### 5.3 The compliance numbers, and three bugs behind them

Final: **max |delta| 1.45 points**, Indic present in **60/60 batches**, cumulative floor minimum
**14.55%** against 14%. Getting there took four fixes, each found by measuring:

| Fix | Before | After |
|---|---:|---:|
| deficits made stage-local, not cumulative | 9.45 | 0.75 |
| OPUS exhaustion fallback so a slot always fills | 29.40 | 4.68 |
| Indic floor measured in tokens, not slots | 4.68 | 1.79 |
| ATOMIC splits between turns instead of dropping | 7.27 | **1.45** |

The second is the instructive failure: a slot whose candidates were all rejected produced
nothing, so the lane was charged no tokens, protected lanes always filled and unprotected ones did
not - and OPUS silently rewrote the mixture to 47% Indic. [`PLAN.md`](PLAN.md) §5.1b has the detail.

```
assignment-6/
  run_demo.py            the one command
  fetch_corpus.py        BUILD-TIME ONLY - never run by run_demo

  tests/test_invariants.py
  submission_artifacts/  run.log, evidence.{json,md}, performance.json,
                         manifests/, ledgers/, checkpoints/, shards/
```

**Self-contained on purpose.** The inputs are vendored, not referenced, because
`assignment-4/data/` and `assignment-5/proxy/data/` are gitignored - a demo reading a sibling's
ignored directory fails on a fresh clone, which is exactly what the grader does. A vendored input
carrying a recorded `sha256` *is* the immutability the brief asks for.

**Continuity.** A2 supplies the frozen tokenizer (10,000 vocab, byte-fallback, frozen months ago for
another purpose - stronger evidence than one minted for this demo). A4 supplies the provenance
discipline that lets the Indic lane carry native/translated tiers. A5 supplies `plan.json`: seven lane
shares, five curriculum stages, the 14% floor, the OPUS parameters. **A6 executes them.**

## 7. Limitations

1. **Training runs at 512 tokens.** NumPy attention is O(n²). Packing correctness is exercised at
   4096 and 32768 in tests without training on them. At 512 the ATOMIC policy drops 14% of agentic
   documents (documents whose *system prompt alone* exceeds the window); at 4096 it drops none.
   Measured, not estimated.
2. **The OPUS scorer is a lexical stand-in.** Real OPUS scores gradient alignment; this scores
   token-profile cosine similarity. The decision lattice, protected override and snapshot-versioned
   replay are faithful; the scoring function is a placeholder and is labelled as one everywhere.
3. **The model is ~560K parameters trained for 60 steps.** Loss falls 9.21 → 5.91. No claim beyond
   that; it exists so the learning ledger contains a real loss linked to real source data.
4. **The Assignment-2 tokenizer never saw code or 9 of the 12 Indic scripts**, so they byte-fall-back
   - measured fertility 0.614 for code and 1.829 for Indic against 0.374 for web. Reported rather
   than hidden.
5. **Corpus slices are small** (23 MB, 8,737 documents). Deliberate: the brief asked for a
   demonstration, not a download.
